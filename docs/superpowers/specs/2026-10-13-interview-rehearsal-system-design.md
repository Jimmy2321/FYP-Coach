> 所属计划：AI Venture Studio

## 一、项目动机（Why）

### 1.1 问题背景

每个毕业生在毕业后都面临两道关卡：

1. **技术面试**（求职路径）：编程思路题、系统设计、行为面试
2. **研究生申请**（深造路径）：学术面试 + 个人陈述

现有市场工具在这两个领域存在明显断层：

- **面试准备工具**（Yoodli、Big Interview、Final Round AI）只关注面试表达，大多收费，面向职场跳槽者而非应届毕业生
- **文书评审工具**（CollegeVine、Grammarly、I'mAdmitted）只管文书写作，不管面试
- **没有任何一款产品同时覆盖面试排练和个人陈述评审**
- 通用 AI（ChatGPT）可以两者兼顾，但缺乏结构化评分标准，输出不稳定，没有面向学生群体的定制化设计

### 1.2 更深层的问题：市面产品都是"测验机"，不是"排练伙伴"

任务描述用的词是 **"rehearses"（排练）**，但目前所有同类产品和学术项目的实际形态都是"测验"：

| 市面通行做法 | 本质 | 缺失了什么 |
|------|------|-----------|
| 静态题库，一问一答 | 笔试 | 真实面试是有来有回的对话，面试官会追问、会施压 |
| 每次练习互不相干 | 一次性测验 | 真实准备是连续的成长过程，弱点需要被追踪 |
| 展示"标准答案"让用户自己悟 | 对答案 | 用户学不会如何改造"自己的"表达 |
| 面试工具和文书工具完全割裂 | 两套独立产品 | 没有任何一款产品同时覆盖这两个场景 |

甚至连 2026 年发表的 RehearsalAI 论文（Next.js + LLM 出题 + 语义相似度评分）也停留在"单轮问答+静态评分"的套路里。**如果只复制这个套路，答辩时"你和现有方案有什么区别"将无从回答。**

### 1.3 为什么值得做

1. **填补市场空白**：没有竞品同时覆盖面试排练 + 申请文书评审；更没有产品让面试具备"读懂简历、动态追问"的排练真实感
2. **重新定义品类**：从"AI 测验机"升级为"AI 排练伙伴"——多轮追问、记忆成长、针对个人简历出题
3. **面向被忽视的用户群体**：主流工具面向有工作经验的跳槽者，毕业生群体被严重忽视
4. **学术可行性已验证**：多篇 2025-2026 年论文证明 AI 辅助面试评分的技术可行性
5. **真实用户可触达**：可直接招集同学测试，这是商业产品做不到的
6. **AI Venture Studio 支持**：导师群组指导 + 年底展示会，提供学术背书和展示机会

## 二、产品定位与差异化（What & How It's Different）

### 2.1 目标用户与两个独立模块

**目标主体**：即将毕业的学生（求职 + 深造两类场景）

产品**提供两个完全独立的入口**，用户可按需选择：

| 模块 | 定位 | 核心能力 |
|------|------|----------|
| **技术面试排练** | 求职面试 + 研究生学术面试的对话式排练 | 简历关键词提取 → 动态多轮追问 → 三维评分 + 成长档案 |
| **申请文书评审** | 个人陈述 / 动机信的结构化评价 | 招生标准对比的多维度评审 + 改写建议 |

两个模块**共享用户身份和成长档案**（面试的成长数据可以在文书评审中提示"你在'结果量化'上的薄弱点也会影响文书写作"），但流程上完全独立——面试模块不依赖文书模块的输入，反之亦然。

### 2.2 技术面试模块的核心支柱（差异化）

面试模块是本项目差异化的核心，三大支柱：

#### 支柱 ①：简历驱动的动态出题（不是通用题库）

**做什么**：用户上传简历（PDF/文字）→ LLM 提取可被追问的技术声明（项目经历、技能、成果）→ 生成针对**这份简历**的面试问题。

**举例**：简历里写"使用 Redis 实现分布式锁"，生成的问题不是"介绍一下你的项目"，而是：
- "你的 Redis 分布式锁具体解决了什么场景的问题？"
- "为什么选 Redis 而不是其他方案（比如数据库行锁、ZooKeeper）？"
- "有没有遇到过锁超时、误删、主从切换的问题？怎么处理的？"

**为什么不同**：Resumly 按 JD 出题但只做单轮问答，Yoodli 有追问但不做内容评分。**"简历关键词提取 + 内容向多轮追问"的组合无直接对标。** 简历本身就是独有题库，每个用户的问题天然个性化——这把"题库规模有限"的劣势变成了特色。

#### 支柱 ②：追问引擎（贴合 "rehearsal" 的本义）

**做什么**：不再是一问一答，而是多轮对话式面试。AI 根据每次回答实时决策下一步动作：
- **深挖（Probe）**：答"用了 Redis 锁" → 追问"为什么选这个方案？"
- **质疑（Challenge）**：答"性能提升了 6 倍" → 追问"基线是什么？负载多少？"
- **切换（Next）**：当前问题答得充分 → 进入下一题
- **收尾（End）**：达到追问深度上限或时间上限 → 结束

**代码约束**：追问层数最多 3 层（代码强制，防无限循环）；同一追问意图不得连续出现两次（防重复）。

#### 支柱 ③：成长档案 + 答案改写

- **成长档案**：跨场次聚合评分数据，生成能力雷达图 + 薄弱点诊断 + 弱点定向出题
- **答案改写**：不展示"理想答案"，拿**用户自己的原答案**做最小编辑改写，标注改动及对应提升的子技能

**共同逻辑**：三个支柱形成"读懂你 → 追问你 → 记住你 → 改写你"的完整排练闭环——这是"排练伙伴"而非"测验机"的本质区别。

### 2.3 申请文书评审模块（MVP：只做评价）

**做什么**：用户上传个人陈述草稿 + 选择目标项目类型（硕士/博士/领域）→ LLM 按招生标准输出结构化评审：

| 评审维度 | 定义 |
|----------|------|
| 个人特质突出度 | 是否展示了独特的个人经历和品质 |
| 叙事连贯性 | 是否有清晰的叙事线，而非经历堆砌 |
| 学术匹配度 | 是否与目标项目/方向匹配 |
| 语言质量 | 语法、用词、表达力 |
| 结构完整性 | 开头-主体-结尾是否完整有力 |

**后续可扩展（Future Work）**：评审报告一键生成针对性面试场次（把文书评审和面试排练缝合成流水线——这是 V2 设计中"PS 联动"的降级实现路径，先做独立评审，再补联动）。

### 2.4 输入方式

两个模块均支持：
- **文字输入**：直接打字
- **语音输入**：Web Speech API 实时转写 → 用户可编辑后提交（识别错误可修正）

### 2.5 与同质化方案对照

| 能力 | 本系统 | RehearsalAI（2026 论文） | Resumly | Yoodli | ChatGPT 直接用 |
|------|--------|--------------------------|---------|--------|----------------|
| 简历驱动动态出题 | 有 | 无 | 有（按 JD） | 无 | 需手动粘贴 |
| 多轮深挖追问（含内容评分） | 有 | 无 | 无 | 有（仅表达） | 需手动引导，不稳定 |
| 成长档案 + 弱点定向 | 有 | 无 | 无 | 部分（表达） | 无记忆 |
| 改写用户原答案 | 有 | 无 | 无（展示理想答案） | 无 | 需手动要求 |
| 文书评审 | 有 | 无 | 无 | 无 | 部分（不稳定） |
| 语音 + 文字输入 | 有 | 无（仅文字） | 有 | 有 | 有 |

### 2.6 核心功能范围（MVP）

| 模块 | 功能 | 优先级 |
|------|------|--------|
| **面试模块** | 简历关键词提取 + 动态出题 | P0 |
| | 多轮追问引擎（含决策逻辑） | P0 |
| | 三维评分 + 子技能标签 | P0 |
| | 答案改写反馈 | P0 |
| | 成长档案（雷达图 + 弱点定向） | P0 |
| | 语音 + 文字输入 | P0 |
| | 面试官人格（和蔼/扑克脸/质疑） | P1 |
| **文书模块** | 五维结构化评审 + 改写建议 | P1 |
| | 文书评审 → 面试联动 | Future Work |

### 2.7 明确不做

| 功能 | 原因 |
|------|------|
| 代码运行环境 | LeetCode/HackerRank 已做得很好，不是本项目核心价值；真实面试考察思路表达 |
| 视频体态分析 | Yoodli/Big Interview 的领域，技术复杂度过高 |
| 实时面试辅助（作弊向） | Final Round AI 的领域，与"排练"定位冲突 |
| 人工面试官匹配 | Interviewing.io/Pramp 的领域，运营成本高 |

## 三、技术方案（How）

### 3.1 技术栈

| 层 | 技术 |
|----|------|
| 前端 | Next.js 14+ (App Router) + React + Tailwind CSS |
| 后端 | Next.js API Routes |
| 数据库 | SQLite (Prisma ORM) |
| AI 能力 | LLM API（GPT-4o-mini 或同类），全部通过 prompt 工程实现，不训练模型 |
| 语音输入 | Web Speech API（浏览器原生） |
| 部署 | Vercel（免费额度） |

### 3.2 系统架构

### 3.3 核心流程：一场多轮面试的完整数据流

```
1. 用户选择面试类型（行为题/编程思路题/学术题）、难度、面试官人格
   （若已上传简历，优先走简历关键词出题）
         │
         ▼
2. 对话引擎生成首题（结合人格 + 用户成长档案中的薄弱子技能定向）
         │
         ▼
3. 用户文字/语音回答 → 存入 Turns 表
         │
         ▼
4. 对话引擎决策（LLM 判断 + 代码约束）：
   ├─ 追问（深挖/质疑）→ 生成追问 → 回到 3（每题最多 3 层追问，代码强制）
   └─ 切换/收尾 → 进入下一题或结束
         │
         ▼
5. 场次结束 → 评分引擎对整场对话评分
   （三维分数 + 子技能标签 + 逐轮反馈 + 答案改写）
         │
         ▼
6. 结果入库 → 档案聚合器更新用户能力档案
         │
         ▼
7. 用户界面：评分报告（含改写对照）+ 档案雷达图更新
```

**关键设计原则**（来自 NYU Stern 论文的工程教训）：决策边界用代码强制，不靠 prompt 自觉——追问深度上限、分数范围 0-100、每轮输出 JSON 格式校验，全部在代码层控制。

### 3.4 简历关键词提取模块（支柱 ①）

**流程**：

```
1. 用户上传简历（PDF / Word / 粘贴纯文本）
         │
         ▼
2. LLM 技术声明提取（prompt 任务：提取所有"可被追问的技术声明"）
   输出 JSON：[{"claim": "使用 Redis 实现分布式锁", "type": "项目技术点", "vague_point": "未说明解决的具体场景"}, ...]
         │
         ▼
3. 用户确认/编辑提取结果（人对提取内容有最终控制权，可删除、补充）
         │
         ▼
4. LLM 逐条生成针对性技术面试问题：
   - 场景类："你这个方案具体解决了什么场景的问题？"
   - 选型类："为什么选 Redis 而不是其他方案？"
   - 细节类："有没有遇到过 XX 问题？怎么处理的？"
   - 深度类："如果让你重新做一遍，你会改什么？"
         │
         ▼
5. 问题入库，标记 source=resume_linked，供面试场次优先选用
```

**技术栈**：简历 PDF → 用 `pdf-parse` 或前端 `FileReader` 提取纯文本 → 传给 LLM。提取失败时用户可手动粘贴简历文本。

**为什么声明提取要用户确认**：LLM 可能误提取或过度推断（比如把"熟悉 Java"推断为"精通并发编程"），用户确认环节把错误挡在面试开始前，也是"可审计性"设计的体现。

### 3.5 追问引擎（支柱 ②）

**决策逻辑**（每轮回答后执行）：

```
输入：当前题目、对话历史（全部轮次）、用户最新回答、已追问层数
约束（代码层）：depth >= 3 时强制切换，不允许继续深挖

LLM 决策 prompt 任务：
  判断最新回答的状态：
  - SHALLOW（泛泛而谈，未触及核心）→ 生成深挖追问
  - UNSUPPORTED（有结论无依据）→ 生成质疑追问
  - COMPLETE（要点覆盖充分）→ 切换下一题
  - OFF_TRACK（跑题）→ 拉回问题主线
输出 JSON：{"action": "probe|challenge|next|redirect", "question": "...", "reason": "..."}
```

**人格对决策的调制**：质疑型人格下 UNSUPPORTED 阈值降低（更容易触发质疑）；和蔼型人格下追问语气软化；扑克脸型不给出任何态度线索。人格只影响 prompt，不影响决策框架代码。

**防循环机制**：同一追问意图不得连续出现两次（代码层比对 LLM 返回的 reason 语义标签）；达到上限或检测到重复时强制切换。

### 3.6 评分引擎

整体方案：**纯 LLM 单次评分**（temperature=0），在初始方案基础上增加**子技能标签**输出，供成长档案聚合。

```
系统角色：经验丰富的面试评分官（人格与面试中使用的一致）

输入：
- 面试题目与全部对话轮次：{turns}
- 标准答案要点：{key_points}
- 题目类型与三维权重：{weights}

输出 JSON：
{
  "correctness": {"score": 0-100, "feedback": "..."},
  "structure":   {"score": 0-100, "feedback": "..."},
  "communication": {"score": 0-100, "feedback": "..."},
  "sub_skills": {
    "result_quantification": 0-100,
    "star_completeness": 0-100,
    "technical_depth": 0-100,
    "terminology_accuracy": 0-100
  },
  "followup_performance": "追问环节表现点评（支柱②独有）",
  "overall_feedback": "总体建议"
}
```

**追问表现单独点评**是本系统特有的评分维度来源：真实面试中"被追问时的应对"恰恰是最暴露能力的环节，单轮问答产品完全没有这个数据。

### 3.7 答案改写模块（支柱 ④）

```
输入：用户原答案、评分结果、该用户薄弱子技能（来自成长档案）
prompt 约束：
  1. 保留原答案的全部事实内容，不得虚构用户没说的经历
  2. 仅做最小编辑：结构调整、量化补充提示、冗余删减
  3. 逐条列出改动及理由，并标注对应提升的子技能
输出 JSON：
{
  "rewritten": "改写后全文",
  "changes": [{"original": "...", "edited": "...", "reason": "...", "skill": "result_quantification"}, ...],
  "score_estimate": "改写后预估分数"
}
```

**红线**：prompt 中明确禁止虚构——改写必须基于用户提供的真实内容，这是学术诚信底线，答辩时可主动声明。

### 3.8 成长档案与弱点定向（支柱 ③）

**档案数据结构**（存 SQLite，非独立服务）：

```
UserProfile {
  dimension_avgs: {correctness, structure, communication},   // 历次滑动平均
  sub_skill_avgs: {result_quantification, star_completeness, technical_depth, terminology_accuracy},
  session_count: int,
  weakest_sub_skill: string,    // 样本数 >= 2 的子技能中平均分最低者
  trend: {last_5_sessions_scores: [...]}
}
```

**弱点定向出题逻辑**：新场次选题时，从题库中优先选取"评分侧重点"命中 weakest_sub_skill 的题目（题库每题预标注侧重子技能标签）。样本不足（< 2 场）时按默认权重选题，避免早期数据噪声误导。

**前端呈现**：雷达图（三大维度 + 子技能）+ 最近 5 场趋势线 + 一句人话诊断："你的表达清晰度不错，但连续 3 场在'结果量化'上丢分——建议练习时强制自己为每个成果配一个数字。"

### 3.9 面试官人格（支柱 ⑤）

实现方式：三份预设 system prompt 片段，在面试开始时装配进出题、追问、评分三个模块的 prompt 中。

| 人格 | 追问倾向 | 语气 | 评分严格度 |
|------|----------|------|-----------|
| 和蔼型 | SHALLOW 才追问 | 鼓励、引导 | 基准 |
| 扑克脸型 | 正常触发 | 中性、无反馈词 | 基准 |
| 质疑型 | UNSUPPORTED 即触发，追问更深 | 直接、连续反问 | 基准（评分标准不变，仅互动风格变化） |

**设计注意**：评分严格度不随人格变化——否则同一人格间的成长档案数据不可比。人格只改变互动风格，这是答辩时可能被打探的设计细节。

### 3.10 申请文书评审模块（独立模块）

```
用户上传 PS 草稿 + 选择目标项目类型（硕士/博士/领域）
  → LLM 按招生标准输出结构化评审（五维）：
    个人特质突出度 / 叙事连贯性 / 学术匹配度 / 语言质量 / 结构完整性
  → 逐维度给出具体改写建议（引用原文 + 改写对照）
```

**与面试模块的关系**：MVP 中两个模块完全独立，文书评审不依赖简历或面试数据。Future Work 中考虑复用面试模块的改写能力，将文书评审的薄弱点自动转化为面试练习题目（闭环）。

### 3.12 语音输入方案

- 浏览器原生 Web Speech API（SpeechRecognition），中英文可切换
- 实时转写 → 用户可编辑后提交（识别错误不直接入档）
- Chrome / Safari 支持；Firefox 自动降级为纯文字
- 语音仅作为输入方式，不做发音/语速分析（明确不碰 Yoodli 的领域）

### 3.13 错误处理

| 场景 | 处理方式 |
|------|----------|
| LLM API 超时 | 重试 1 次，仍失败提示重新提交，当前对话进度已入库不丢失 |
| LLM 返回非合法 JSON | 代码层 JSON 校验 + 正则兜底提取分数；仍失败标记"评分异常"允许手动重评 |
| 追问决策异常 | 决策 action 非法时降级为 next（切换下一题），保证流程不死锁 |
| 语音识别失败 | 降级纯文字，识别结果永远可编辑 |
| 数据库写入失败 | 前端保留答案副本，提示稍后查看 |

### 3.14 成本估算（多轮对话后的更新）

单场面试（5 题 × 平均 2 层追问 + 评分 + 改写）约 12K-18K token，GPT-4o-mini 下单场成本约 $0.008-0.015。即使用户测试阶段 15 人 × 每人 5 场 = 75 场，总成本不到 $1.5。成本不是风险，但仍在代码中设月度调用上限以防失控。

## 四、如何做好：质量与可信度策略

### 4.1 评分可信度是生死线

- **金标准测试集**：选 5-10 道题，每题手写 3 个质量明显不同的答案（好/中/差），请同学/导师盲排序。验证 AI 评分排序与人工排序一致（Kendall's tau > 0.7 为达标）。这是答辩时最有力的证据。
- **一致性回归测试**：同一答案连评 3 次，方差 < 10 分。每次改 prompt 后重跑金标准集回归，确认评分无漂移。
- **prompt 版本化管理**：所有评分/追问/改写 prompt 存为独立配置文件（不硬编码），每次修改记录版本号与变更原因，可回滚，答辩可展示迭代史。

### 4.2 题目与反馈质量

- 题目从**真实面经**采集（牛客网、一亩三分地、Glassdoor、知乎面经帖），非凭空编造
- 每题"标准答案要点"LLM 生成后**人工审核**并记录审核过程（可审计性）
- 反馈强制"引用学生原话 + 给出具体改写示例"，杜绝"表达可以更清晰"式废话（支柱 ④ 从机制上保证这点）

### 4.3 评估防"人情分"

- 同学测试用**匿名问卷**，不当面询问
- 三方对照：AI 评分 vs 学生自评 vs 同伴互评，计算相关性——AI 与人类判断基本一致，评分体系即立住
- 量化指标**预先定义**（第六章目标值），测完拿数据对照，而非测完再定标准

### 4.4 工程质量

- 出题 / 追问决策 / 评分 / 档案聚合**四模块独立**，可单独测试（NYU Stern 论文教训：单体 prompt 智能体不可靠，拆分为单一职责模块）
- 行为约束在代码层（追问深度、分数范围、JSON 校验），不靠 prompt 自觉

### 4.5 答辩辩护预演

| 可能的质疑 | 准备好的回答 |
|-----------|-------------|
| "评分怎么保证可信？" | 金标准测试集 + 一致性方差数据 + 三方对照实验 |
| "和直接用 ChatGPT 有什么区别？" | 结构化 rubric、追问决策引擎、成长档案记忆、PS 联动——ChatGPT 是通用工具，这是有状态、有方法论的专门系统 |
| "和 RehearsalAI 论文有什么区别？" | 它是单轮问答+静态评分；我们有多轮追问、改写反馈、成长档案、文书联动，四大差异点逐一对比 |
| "为什么不做代码运行环境？" | 有意排除：真实技术面试考察思路表达而非代码能否运行，LeetCode 已覆盖后者 |
| "LLM 评分有随机性怎么办？" | temperature=0 + 实测方差数据；语义相似度方案作为 future work |
| "AI 改写会不会帮学生造假？" | prompt 红线禁止虚构经历，改写仅基于用户真实内容，诚信边界在设计文档中明确声明 |

### 4.6 展示会（Showcase）策略

- 现场 demo 之外**必须准备录屏备份**（防现场网络/API 故障）
- 最佳演示动线：上传 PS → 30 秒生成针对性问题 → 现场答一题 → 触发追问 → 展示改写对照 → 切质疑型人格再答一次 → 展示档案雷达图变化。一条动线把五大支柱全部点亮
- 准备一个"前后对比"案例：同一同学第 1 场与第 5 场的评分报告对比

### 5.2 核心竞争优势（客观评估）

#### 优势 1：同时覆盖技术面试排练 + 文书评审（两个独立模块）

**事实**：无任何商业或学术产品同时提供这两个场景的服务。面试工具与文书工具是完全隔离的两个市场——Yoodli、Resumly 只做面试；CollegeVine、I'mAdmitted 只做文书。

**客观性说明**：两个模块在 MVP 中独立运行，联动（文书评审 → 面试题目转化）列为 Future Work。此优势当前体现为"在同一产品中能做两件事"，而非"两件事自动联动"。但即便独立，"两个入口、一次注册、共用成长档案"的体验也是分散使用两三款产品无法比拟的。

#### 优势 2：简历驱动 + 多轮追问的排练真实感

**事实**：市面产品要么按静态题库出题（Warmup、RehearsalAI），要么按 JD 出题但无多轮追问（Resumly），要么有追问但只评表达不评内容（Yoodli）。**"简历关键词提取 → 针对性出题 → 内容向多轮追问"的组合无直接对标。**

**客观性说明**：追问质量高度依赖 LLM 对话能力，存在追问生硬、重复的风险（需防循环机制缓解）。真实面试官的追问还包含非语言信息（表情、停顿），文字/语音转写无法完全还原。

#### 优势 3：成长档案把数据变成教练计划

**事实**：竞品的练习历史均为静态回放。本项目的弱点诊断 + 定向出题形成训练闭环。

**客观性说明**：档案的准确性随样本量增长，前 1-2 场的诊断可信度低（设计中已用样本阈值缓解）。且子技能标签本身由 LLM 生成，标签体系未经过心理测量学验证。

#### 优势 4：改写式反馈的教学优势

**事实**："展示理想答案"（Resumly 等）与"改写你的答案"是两种不同的教学范式，后者学习迁移效果更好，且结合个人薄弱档案实现千人千面。

**客观性说明**：这是设计哲学优势而非技术壁垒——竞品要模仿不难。护城河在于它与成长档案、追问数据的联动，单独的改写功能不构成壁垒。

#### 优势 5：评分透明可审计 + 真实用户验证

**事实**：评分 rubric、权重、prompt 全部公开；可直接招集同学做对照实验验证评分有效性。

**客观性说明**：透明不等于准确；同学样本量有限（5-15 人）且存在人情分风险，需匿名问卷缓解。学术背书增加可信度，但工程成熟度不及商业产品。

### 5.3 客观劣势评估

#### 劣势 1：功能丰富度不足

无视频体态分析、代码运行环境、实时辅助、人工匹配。**缓解**：明确范围边界，强调"做精而非做多"；答辩时主动声明排除理由。

#### 劣势 2：LLM 评分与追问的随机性

纯 LLM 评分存在输出漂移；追问质量不稳定。**缓解**：temperature=0、金标准回归测试、追问防循环代码约束；语义相似度方案列为 future work。

#### 劣势 3：题库规模有限

预置题库无法与 Big Interview / LeetCode 相比。**缓解**：简历驱动出题（每个用户的简历本身就是独有题库——这把"题库规模有限"的劣势转化为"个性化出题"的特色）。

#### 劣势 4：缺乏行业数据支撑

无真实企业面试官数据、无院校合作数据。**缓解**：用户测试收集"AI 评分 vs 自评 vs 互评"对照数据；答辩中明确定位为初步验证。

#### 劣势 5：用户留存天然较低

毕业生使用周期短（数月）。**缓解**：不追求留存，定位"关键时期的锐利工具"；学术项目不以 LTV 论成败。

#### 劣势 6：工程成熟度

性能优化、并发、安全等不及商业产品。**缓解**：明确定位"学术原型"，展示会以演示路径受控的方式进行。

### 5.4 竞争力总结

| 维度 | 评价 |
|------|------|
| 功能广度（面试+文书） | **领先**，无直接竞品 |
| 排练真实感（简历+追问） | **领先**，无内容向追问竞品 |
| 个性化（档案+定向+改写） | **领先**，竞品均为静态 |
| 评分稳定性 | **劣势**，纯 LLM 评分有随机性 |
| 题库规模 | **中性**，简历驱动部分对冲 |
| 工程成熟度 | **劣势**，定位学术原型 |
| 成本 | **优势**，完全免费 |

**定位声明**：本项目不与商业产品比功能丰富度和工程成熟度，也不复制学术同行的"单轮问答+静态评分"套路。其核心竞争力在于：以"排练伙伴"而非"测验机"重新定义 AI 面试准备——读懂简历、动态追问、记忆成长，并在同一产品中覆盖申请文书评审。作为学术项目，其价值在于验证"有记忆、会追问、懂背景的 AI 面试官"这一形态的可行性。
